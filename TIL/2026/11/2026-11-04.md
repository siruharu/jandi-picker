  - 만약에 Docker 를 사용한다면 컨테이너로도 실행할 수 있다
  - 그런데 운영 환경에서 다음과 같은 문제가 발생한다면?
- Kubernetes의 기본 구조
  - 개념 이해를 위한 간단하게 구성된 구성도. 실제 Control Plane에는 etcd 등 다른 구성 요소도 있고, 노드 구조도  더 복잡함
- Cluster(클러스터)
  - Kubernetes로 관리되는 전체 시스템이다. Control Plane과 하나 이상의 Node로 구성돼. 여러 서버를 하나의 운영 환경처럼 관리한다고 이해하면 됌
- Node (노드)
  - Pod 가 실행되는 물리 서버 또는 가상 서버다.
  - 예를 들어 AWS EC2 인스턴스가 Kubernetes Worker Node로 사용될 수 있다.
- Pod (파드)
  - Kubernetes에서 컨테이너를 실행하는 가장 작은 배포 단위
  - 보통 Pod 하나에 어플리케이션 컨테이너 하나만 실행되지만, 필요하면 여러 컨테이너를 포함할 수 있다.
- 예를 들면 Spring Boot 어플리케이션 3개를 실행하고 싶다면, 일반적으로 동일한 어플리케이션 컨테이너를 가진 Pod 3개를 Deployment로 관리하는 방식
- kubectl 은 무엇인가?
  - `kubectl`은 Kubernetes의 클러스터에 명령을 전달하는 CLI 도구이다.
  - 실제로는 Kubernetes API Server와 통신해서 리소스 조회, 생성, 수정, 삭제한다
  - 명령어의 기본 형태는 다음과 같다
  - 오늘 볼 명령어는 3개
  - `kubectl get nodes` : 클러스터에 있는 Node를 조회
  - `kubectl get pods` : 현재 Namespace의 Pod조회
  - `kubectl get pods -A` : 모든 Namespace의 Pod 조회
- Killercoda에서 직접 실행해보기 (https://killercoda.com/playgrounds/scenario/kubernetes?utm_source=chatgpt.com)
  - `kubectl get nodes`
  - `kubectl get pods`
  - `kubectl get pods -A`
  - 여기서 중요한 것은 우리가 Pod를 생성하지 않았음에도 기본적인 Kubernetes 자체가 사용하는 Pod가 존재한다는 사실을 알아야한다.
  - `etcd-controlplane` : Kubernetes 클러스터 상태 데이터 저장
  - `kube-apiserver-controlplane` : Kubernetes API 요청 처리
  - `kube-scheduler-controlplane` : Pod가 실행 될 Node 결정
  - `kube-controller-manager-controlplane` : 리소스의 원하는 상태 유지
  - `coredns` : Kubernetes 내부 DNS 처리
  - 여기서 기억해야 할 것은 네가지
  - `kubectl run my-nginx --image=nginx:stable`
  - `kubectl get pods -o wide`
  - `NAME` : 생성된 Pod 이름
  - `READY` : 컨테이너 1개 중 1개가 준비됨
  - `STATUS` : Pod 상태
  - `RESTARTS` : 컨테이너 재시작 횟수
  - `AGE` : Pod 생성 후 경과 시간
  - `IP` : Pod에 할당된 내부 IP
  - `NODE` : Pod가 실행되는 노드
  - 여기서 중요한 것은 Pod IP와 Node는 서로 다르다는 것
  - `kubectl describe pod my-nginx`
  - 실행 결과에서 나오는 주요 항목
  - 여기서 `Events` 는 나중에 CKA 장애 해결 문제에 매우 중요하다. -> 예를 들어 이미지 다운로드 실패, 스케줄링 실패 등을 분석할 때 사용된다.
